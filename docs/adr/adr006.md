ADR006 – Saga Pattern pour les transactions distribuées

Statut : Acceptée
Date : 2025-11-20
Fichier : /docs/adr/adr006.md

Contexte

Dans une architecture microservices, les opérations métier (comme l'annulation ou la modification d'ordre) nécessitent souvent la coordination de plusieurs services (OrderService, WalletService, MatchingService, EmailService). Les transactions distribuées ACID traditionnelles ne sont pas applicables dans ce contexte, car chaque service a sa propre base de données. Il faut donc un mécanisme pour garantir la cohérence des données lors d'opérations multi-services.

Décision

Adopter le pattern Saga avec orchestration centralisée. L'OrderSagaOrchestrator coordonne les étapes séquentielles des transactions distribuées :
- Annulation d'ordre : mise à jour statut → annulation matching → remboursement → notification WebSocket → email
- Modification d'ordre : validation → annulation matching → mise à jour → re-matching → notification → email
En cas d'échec d'une étape, des mécanismes de compensation sont prévus pour maintenir la cohérence.

Conséquences

+ Garantit la cohérence éventuelle des transactions multi-services
+ Permet une gestion centralisée des workflows complexes
+ Facilite le debugging et le monitoring des opérations distribuées
- Augmente la complexité du code avec la logique de compensation
- Introduit une latence supplémentaire due aux appels séquentiels
- Nécessite une gestion rigoureuse des timeouts et retry policies

Alternatives considérées

Two-Phase Commit (2PC) - Trop rigide et bloquant pour les microservices
Choreography-based Saga - Plus difficile à déboguer et monitorer
Event Sourcing - Trop complexe pour le contexte académique
