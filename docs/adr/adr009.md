ADR009 – Architecture Event-Driven avec RabbitMQ

Statut : Acceptée
Date : 2025-11-20
Fichier : /docs/adr/adr009.md

Contexte

La communication synchrone entre microservices crée un couplage fort et des points de défaillance en chaîne. Les opérations de trading impliquent plusieurs services qui doivent être coordonnés mais peuvent tolérer une cohérence éventuelle. Une architecture événementielle permettrait un découplage plus important et une meilleure résilience.

Décision

Adopter RabbitMQ comme message broker principal pour la communication asynchrone inter-services. Les événements métier (OrderPlaced, OrderCancelled, OrderModified, TradeExecuted) sont publiés dans des queues dédiées. Chaque service s'abonne aux événements qui le concernent via @RabbitListener. Cette approche est complémentaire aux appels synchrones (Feign) pour les opérations nécessitant une réponse immédiate.

Conséquences

+ Découplage temporel entre les services
+ Résilience améliorée (tolérance aux pannes temporaires)
+ Scalabilité horizontale facilitée
+ Support natif du pattern Publish/Subscribe
- Complexité accrue dans le debugging des flux asynchrones
- Gestion des messages en erreur (Dead Letter Queues)
- Cohérence éventuelle vs immédiate selon les cas d'usage

Alternatives considérées

Apache Kafka - Overkill pour le volume et complexité du projet académique
Redis Pub/Sub - Pas de persistance des messages
Amazon SQS/SNS - Dépendance cloud, complexité pour l'environnement de développement
